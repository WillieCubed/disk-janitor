# Deterministic local jobs

Willie's requested interface is `disk-janitor submit -- COMMAND`, followed by conventional `status [JOB]`, `logs JOB`, `wait JOB`, and `cancel JOB`. No agent-supplied budgets, storage roots, owner labels, scheduling classes, or restartability policy. Every submission is a distinct job; identical commands are not conflated. Existing `run` cleanup and `guard` callers remain compatible and are omitted from the normal job help.

The existing guard remains the single admission authority. A durable, private job record and a permission-preserving background worker adapt submissions to that authority. There is no second queue broker or privileged daemon executing submitted commands. Workers inherit the submitting execution environment and its sandbox/approval context; observers never replay a stored command in a different permission context. A stable backend job ID lets a surviving guardian publish an outcome after a worker/client crash. Without trustworthy execution/outcome evidence, the observable terminal state is Unknown, never an invented success or automatic replay of an arbitrary command.

Deterministic built-in profiles select resource estimates. Executable names cannot establish transitive effects: all ordinary submissions remain nonrestartable with conservative cache exclusion. The guard owns fairness, physical admission, cache leases, cancellation, teardown and bounded cooperative retry. Automatic recovery is pressure-driven, reclaims only the three already-authorized inactive cache categories, and stops when actual capacity meets the waiting demand. A bounded global maintenance drain prevents cache-recovery starvation while preserving unknown and legacy users. Selective category leases are deferred until a controlled transitive runner contract exists. User artifacts and outputs outside those cache categories are never automatically deleted. Job metadata and bounded diagnostic logs are managed independently of command artifacts.

Use the existing shared Cargo configuration and pnpm clone linking. Account for CWD, cache/temp and artifact filesystems; preserve the 20 GiB internal and 100 GiB declared external reserve. Default managed output paths are allocated by the tool. Do not create disk images or copy source environments implicitly. Missing required mounts defer work; do not create replacement mount directories. Preserve RunnerPools' scheduling boundary and avoid double reservation under a verified existing guard.

TLA+/TLC will check a finite model of admission, leases, cleanup, cancellation, crash/outcome uncertainty and bounded safe retry. Claims are protocol properties, not a proof of arbitrary command I/O or exactly-once external effects. Liveness assumes fair execution, returning capacity and an available authorized executor; Unknown is a settled protocol outcome when proof is lost. The final report must state model bounds and assumptions, runtime conformance tests, and measured concurrency/throughput.

Approach: extend the existing deterministic guard protocol with durable job submission rather than introduce a competing daemon scheduler. The tradeoff is one lightweight permission-preserving worker per submitted job; this avoids weakening the platform's approval boundaries and keeps controller failure recovery within existing guardian semantics.
